A task is Silieco's basic unit for organizing work: a feature, a bug, an investigation — anything a member or an agent should own and drive forward. The discussion around it, its status changes, and every run stay in one place, so there is no need to reassemble context from chat logs or terminal output.

## Parts of a task

| Part | Purpose |
|---|---|
| **Title and description** | Goal, background, requirements, and acceptance criteria. |
| **Status and priority** | Where the work stands and what to handle first. |
| **Assignee** | A workspace member, an agent, or a squad. |
| **Dates, labels, and custom properties** | Planning, categorization, and your team's own fields. |
| **Project and parent-child relationships** | Fits into a larger body of work, or splits into sub-tasks. |
| **Activity and execution log** | Comments, status changes, runs, and results returned by agents. |


## Create a task

Create one from the **Tasks** page or inside a project — a title is enough, and every other property can be filled in later.

Each task has a number, such as `SILI-123`. The digits increment within the workspace; after an admin changes the workspace's task prefix, numbers display with the new prefix. See [Workspaces](/workspaces#create-a-workspace).

## Choose an assignee

| Assignee | Effect |
|---|---|
| **Member** | That member owns the follow-up; no run is created. |
| **Agent** | A run is created for that agent. |
| **Squad** | The squad leader receives it and decides who handles it. |

When assigned to an agent or a squad, the task enqueues immediately unless it is in `backlog`; if the runtime is offline, the run waits in the queue. Archived agents and squads cannot be assigned.

Assignment does not bypass an agent's Access; when assigning to a squad, the leader's Access is what gets checked. See [Assign tasks to agents](/assigning-tasks).

## Status

| Status | Meaning |
|---|---|
| `backlog` | Not starting yet. A task assigned to an agent only creates a run after it leaves `backlog`. |
| `todo` | Scoped and waiting to start. |
| `in_progress` | Being worked on. |
| `in_review` | Has a result waiting for review. |
| `done` | Finished. |
| `blocked` | Cannot continue for now. |
| `cancelled` | No longer pursued; the record stays. |

There is no fixed flow between statuses — members and agents can change them directly.

Once a task is assigned to an agent, the agent is expected to move the status from `backlog` / `todo` to `in_progress` when it starts, then to `in_review` when it has delivered. These updates are written explicitly by the agent through the Silieco CLI during the run — the server does not flip task status when a run starts or completes (apart from the two system exceptions below). `done` is usually a human confirmation, or an integration such as a PR with close intent that merges.

<Callout type="info">
Two changes are made by the system:

- When a run fails, the task has no other runs, and no retry is triggered, `in_progress` rolls back to `todo`.
- When a linked GitHub PR merges with close intent and no other linked PR is still open or draft, the task becomes `done`.
</Callout>

## Tasks and runs

A task is the persistent record of a piece of work; a [run](/runs) is one concrete run by an agent. One task can produce several runs over time — a first implementation, follow-up changes, another check. A completed run only means that run ended; whether the task is finished is determined by the task's status.

## Projects and sub-tasks

A task belongs to at most one [project](/projects); the project provides shared instructions and resources for runs inside it. Moving a task to another project does not create a copy.

Larger work can be split into sub-tasks: the parent task keeps the overall goal while sub-tasks progress independently. Parent and child statuses do not affect each other.

Sub-tasks can be given a **stage** to advance in batches — 1, 2, 3. When every sub-task in the earliest unfinished stage reaches `done` or `cancelled`, the parent task receives a "sub-tasks completed" notification; when the parent's assignee is an agent, it wakes up and decides whether to start the next stage. Sub-tasks without a stage count as one batch and notify once when they all finish.

## Switch views

The Tasks page offers five views — list, board, table, Gantt, and swimlane — filterable and sortable by status, assignee, project, and other properties. They all show the same tasks.

## Delete a task

Any workspace member can delete a task.

<Callout type="warning">
Deletion cannot be undone: the task with its comments, attachments, and linked records is permanently removed, and unfinished runs are cancelled. When the work is simply no longer pursued, set the status to `cancelled` instead — the discussion and results stay available.
</Callout>
